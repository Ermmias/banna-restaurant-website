Getting web orders to charge and print

Banna Restaurant & Bar · MID 526627181880 · (214) 758-0752 · Banna9560@gmail.com

Where we actually are: the website's cart and card form are written and working, but the payment piece was never switched on live. Right now the site collects the guest's name, phone and order and we call them back. Nothing is broken for guests — it's just not automated yet. Five things below are what stand between us and a card charging itself and a ticket printing in the kitchen.

Open this question first

"I already have Clover Online Ordering at banna-restaurant.cloveronline.com. Does that already take payment and print to my kitchen printer automatically? If so, what do I need to switch on to make that happen?"

If the answer is yes, that is the cheapest path and most of the rest of this sheet becomes unnecessary — we point every "Order" button on the website at the Clover page and we're done. Only if Clover Online Ordering can't do what you need (or takes too big a cut) do we go back to the custom setup, and then questions 1–5 matter.

1. The two API tokens

The hiccup: taking a card online needs two different credentials and it isn't obvious which is which. A REST API token (to read the menu and write the order into the POS) and an Ecommerce API private token (to actually charge the card). The public key alone cannot charge anything.

Ask: "Please confirm my merchant has the Ecommerce API enabled, and walk me to where I create the private eCommerce iFrame token and the REST API token. Do both need specific permissions — inventory read, orders write, payments — and are they enabled on my account?"

2. reCAPTCHA on the card form

The hiccup: reCAPTCHA is turned on for the iFrame token on your account. When it's on, the card form fails to produce a token unless the merchant ID is passed alongside the key — and the error it gives is unhelpful, which is exactly the kind of thing that eats an afternoon.

Ask: "Under Ecommerce API Tokens → reCAPTCHA Settings, is reCAPTCHA on for my token? Should I leave it on, and what domains do I need to allow-list for bannarestaurant.com?"

3. The money showing as PAID in the POS

The hiccup: the charge going through and the order appearing in Clover are two separate steps. To mark the order paid, Clover needs an "External Payment" tender on the merchant account. If that tender doesn't exist, the order lands in Clover as unpaid — which is how staff end up charging a guest a second time at the counter.

Ask: "Does my merchant account have an External Payment tender enabled? If not, please enable it. And is that the correct tender for a card already charged through the Ecommerce API, so it reports as collected online and not as a second sale?"

4. The ticket actually printing in the kitchen

The hiccup — and the one that matters most: creating an order through the API does not print it. Clover has to be told to fire a print event, and that only reaches paper if a device on your account is set up as the order/kitchen printer and is online. An order can be paid, sitting in Clover, and nobody in the kitchen ever knows.

Ask, in this order:

  • "When an order is created through the REST API, will it automatically print to my kitchen printer, or do I have to send a separate print event?"
  • "Which of my devices is configured as the order printer, and is it set to auto-print incoming online orders?"
  • "Do I need the Order Printing app, or a printer profile / print group assigned, for API-created orders to reach that printer?"
  • "Is there an order type I should tag online orders with — pickup or online — so they route to the right printer and show correctly on the Orders screen?"

Also worth asking: "If a printer is offline when the order comes in, does the ticket queue and print later, or is it lost?"

5. Tax matching

The hiccup: the website calculates tax at 8.25%, and Clover applies its own tax settings to the order it creates. If those two don't match, the amount charged and the POS total disagree by a few cents on every order — messy at reconciliation.

Ask: "What tax rate is configured on my items, and is tax applied automatically to orders created through the API? Should I send the order with tax already included, or let Clover add it?"

One more thing to confirm while you have them

Every dish you want sold online has to exist in Clover inventory with a price set — the website deliberately refuses to sell an item the POS doesn't recognise, so nobody can order a $40 platter for $4. Ask them to confirm your online-sellable items are all in inventory and priced.

And ask: "Is my account on production or sandbox for the Ecommerce API, and does my first live order move real money?" (It does — so the first test should be one cheap item on your own card, then refund it from Transactions.)

What to tell me after the call

  1. Whether Clover Online Ordering can already handle payment + printing (yes/no).
  2. Whether the External Payment tender is now enabled.
  3. Which device is the order printer, and whether API orders auto-print.
  4. The order type name to use for online/pickup orders.
  5. Your item tax rate, and whether Clover adds tax to API orders.

Never read your private tokens out loud, email them, or paste them into a chat. If Clover needs to see one, do it inside their dashboard. If a private token has ever left your own screen, delete it in Clover and create a new one — it takes a minute.
